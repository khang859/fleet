# Agent Pane MCP Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let the native Agent pane connect to external MCP servers, so their tools join the agent's own ten.
Covers stdio and Streamable HTTP transports, full OAuth 2.1 authentication, and one-click import of servers already configured for Claude Code and OpenCode.

**Architecture:** A new `src/main/agent/mcp/` module owned entirely by the Agent pane.
`McpManager` holds one `Client` per enabled server from `@modelcontextprotocol/client`, keeps the authoritative wire-name to (server, tool) route map, and exposes tool specs to the turn loop.
`agent-tools.ts` gains a `mcp` parameter on `toolSpecsFor`, and `run.ts` routes namespaced names to the manager before its switch.
MCP calls pass through the existing `PermissionGate` on a new rule set that is separate from the shell-command rules.
OAuth runs through a `FleetOAuthProvider` implementing the SDK's `OAuthClientProvider`, with a loopback callback server and tokens encrypted by `safeStorage`.
Import reads Claude Code and OpenCode configs at both user and project scope, normalises them to Fleet's own shape, and records provenance so a re-scan can report what is new or changed.

**Tech Stack:** Electron (main = Node, ESM output), `@modelcontextprotocol/client` v2, `zod@4`, Electron `safeStorage`, `electron-store`, `shell-env`, React + TypeScript, Zustand, Tailwind + Fleet semantic tokens, `lucide-react`.
Tests: Vitest.

**Decisions taken before writing this plan:**

- The Agent pane gets its own MCP stack. Chat's existing `src/main/chat/mcp/` is left completely untouched.
- Adopt the official SDK rather than extending the hand-rolled JSON-RPC client.
- Full OAuth 2.1 in this build, not deferred.
- Import copies servers into Fleet as independent, editable entries, and is re-scannable.
- Import sources are Claude Code and OpenCode only, at both user and project scope.
- Everything lands as one PR on `feat/agent-mcp`.

## Global Constraints

- **No unsafe type assertions (`as`) or `eslint-disable` in `src/`.** Use zod or explicit narrowing for runtime data. Eslint enforces this in `src/` and allows casts in tests.
- **Never use the em dash.** Use a plain dash.
- **Two new runtime dependencies only:** `@modelcontextprotocol/client` and `@modelcontextprotocol/core`. Pin both to exact versions. No TOML parser, because Codex is out of scope.
- **Wire tool names must fit 64 characters** and match `^[a-zA-Z0-9_-]{1,64}$`. This is the binding limit for Anthropic, OpenAI and Gemini, and OpenRouter passes names through to the provider. The composed `mcp__server__tool` form overflows on real servers.
- **Wire names must be deterministic across restarts.** The model sees a stable tool list, and a session log replayed later must still route.
- **Secrets never cross IPC to the renderer in plaintext.** The renderer learns presence, never the value. This matches `ChatSecrets`.
- **Secrets never land in `fleet-settings.json`.** That file is plaintext on disk. Tokens, bearer values and secret-shaped header or env values go through `safeStorage` into a separate store.
- **stdio servers must spawn with the login shell's PATH.** An Electron app launched from Finder inherits a minimal PATH, and every `npx`-based server fails with ENOENT. Use the existing `shell-env` dependency.
- **The agent's own ten tools keep their hand-written schemas.** MCP specs are appended, never merged into `AGENT_TOOL_SPECS`.
- **Settings read = defaults merged under stored values.** No migration. `mcpServers` defaults to `{}`.
- **Verification commands:** `npm run typecheck`, `npm run lint`, `npm run build`. Full suite: `npm run test` (never `npx vitest run` directly after `npm run dev`, because the sqlite addon is then Electron-ABI).
- **Tests** live in `__tests__/` dirs named `*.test.ts`. Renderer components are not unit-tested in this repo. Verify them via typecheck, lint, build and a manual smoke through `npm run drive`.

## Phase 1: Naming and types

The naming function comes first because everything downstream depends on it, and because it is the one piece with a known-broken precedent in every shipping harness.

- [ ] **1.1** Write `src/shared/agent-mcp.ts` with `McpServerConfig` (`command`, `args`, `env`, `url`, `headers`, `enabled`, `auth`, `disabledTools`, `importedFrom`), `McpServersConfig`, `McpTransportKind`, `McpConnectionState` (`connected` | `connecting` | `needs-auth` | `failed` | `disabled`), `McpToolSummary`, `McpServerStatus`, and `transportOf`.
  Note in a comment that `needs-auth` is a distinct state from `failed`, because it is actionable by the user rather than a fault.
- [ ] **1.2** Write `src/shared/agent-mcp-names.ts`.
  `wireToolName(server, tool)` sanitises both halves to `[A-Za-z0-9_-]`, composes `mcp__server__tool`, and when the result exceeds 64 characters truncates to a readable head plus `_` plus a 6-character hash of `server + "\0" + tool`.
  Export `isMcpToolName`.
  The hash must be a stable non-cryptographic digest computed in-process, not `crypto.randomUUID`.
- [ ] **1.3** Tests for `agent-mcp-names.ts`: short names pass through unchanged; over-long names land at exactly 64; sanitising strips dots and slashes; two different (server, tool) pairs that truncate to the same head produce different names; the same pair produces the same name across calls.
  Verify: `npm run test -- agent-mcp-names`.
- [ ] **1.4** Add `mcpServers: McpServersConfig` to `AgentSettings` in `agent-types.ts` and to `DEFAULT_AGENT_SETTINGS` as `{}`.
  `settings-store.ts` hand-rolls its deep merge in **two mirrored places**, `get()` (around line 78) and `set()` (around line 143).

## Phase 3: Wiring into the turn

- [ ] **3.1** Widen the tool-spec type.
  `AgentToolSpec.function.name` is currently typed `AgentToolName` (`agent-tools.ts:262`), a closed union, so an MCP spec will not typecheck as-is.
  Split the type: keep `AgentToolSpec` exactly as it is for the native ten, and add `ExternalToolSpec` with `name: string` for MCP.
  `toolSpecsFor` returns `Array<AgentToolSpec | ExternalToolSpec>`.
  Do not simply loosen `AgentToolName` to `string`. The closed union is doing real work everywhere else, and the point of the split is that the two kinds of tool genuinely differ in who guarantees the name.
- [ ] **3.2** Change `toolSpecsFor` to take `{ image: boolean; mcp: ExternalToolSpec[] }` and append the MCP specs after the native ones.
  Add the prose passage explaining that MCP tools are the user's rather than the app's, in the voice of the surrounding file.
- [ ] **3.3** In `agent-service.ts`, obtain the MCP specs from the manager when building a turn and pass the manager through `AgentToolContext`.
- [ ] **3.4** In `tools/run.ts`, add the namespaced-name branch before the switch, so an MCP call never reaches `parseArgs`'s native path.
  Return a result shaped like every other tool's, with a summary line naming the server.
- [ ] **3.5** Handle MCP image content.
  An MCP `tools/call` result may carry image blocks, and the completions API allows only text in a tool-result message.
  Reuse the existing side channel: `agent-service.ts:264-268` already sends a following user message for `AgentToolResult.image`, so write the image to the agent image store and populate that field rather than inventing a second mechanism.
- [ ] **3.6** Mention connected MCP servers in `buildSystemPrompt` (`agent-types.ts`), which describes the tool set in prose alongside the JSON schemas.

## Risks

- **`@modelcontextprotocol/client` v2.0.0 went GA on 2026-07-27**, ten days before this plan.
  The v1 line at `@modelcontextprotocol/sdk@1.30.0` is the fallback, at the cost of the cached discovery state and SEP-2352 issuer binding that make the OAuth path clean.
  Pin exactly and be ready to move.
- **Tool-name overflow is an unsolved problem across the ecosystem.**
  Claude Code has open 400-error bugs from exactly this.
  Phase 1 exists to get ahead of it, and its tests are the ones that matter most.
- **stdio spawning in a packaged app** is the most likely thing to work in dev and fail once shipped.
  The login-shell PATH work in 2.3 is not optional.
- **Tool volume** grows fast once import works. Four servers can exceed a hundred tools, well past the range where model accuracy holds. The counter and per-tool checkboxes are the mitigation.
- **Tool calls in a round run sequentially**, by deliberate design (`agent-service.ts:507`, so todo-tool call ids are minted against settled list state).
  MCP calls inherit that. Three calls to a slow HTTP server in one round will feel slow, and this plan does not change it.
  If it turns out to matter, the fix is to parallelise only MCP calls, which carry no shared state, and leave the native tools sequential. Out of scope here.
- **The agent's tool set is a closed world on purpose.**
  The module comment at `agent-tools.ts:1-32` argues for exactly ten tools that deliberately do not overlap.
  MCP breaks that on the user's instruction rather than by accident, and the prose added in 3.2 should say so plainly rather than quietly appending to a list that spends thirty lines explaining why it is short.
